## Задача этой сессии: свои приёмные пункты (locations) — создание,
## редактирование, архивирование без потери отчётности

Павел попросил: дать возможность создавать/редактировать/удалять свои
приёмные пункты, но так, чтобы удаление не ломало отчётность
(историю заказов, перемещений). Ниже — план, согласованный с ним в
переписке перед этим HANDOFF, реализовать его без пересогласования.

### Почему это не требует новой сущности

В `server/src/database/schema.js` уже есть `Location` (tableName
`locations`, строки ~111-123):

```js
Location: tenantEntity(
  {
    branchId: uuid({ tableName: 'branches', key: 'id' }),
    code: string(32),
    name: string(),
    type: string(32), // free-text, сидированные значения: 'acceptance', 'delivery', 'production', 'branch'
    ...archived,       // archivedAt: DATE, nullable — это и есть soft-delete
  },
  {
    tableName: 'locations',
    indexes: [{ unique: true, fields: ['branchId', 'code'] }],
  },
),
```

`Order.acceptanceLocationId` / `Order.issueLocationId`,
`TransferDocument.fromLocationId/toLocationId`,
`ItemMovement.fromLocationId/toLocationId` — всё это уже ссылается на
`locations.id`. Значит, "приёмный пункт" = запись `Location`
(обычно с `type: 'acceptance'`, но CRUD не обязан жёстко резать по
типу — тип просто поле формы с select).

**Мягкое удаление в этом проекте — везде через `archivedAt`, никогда
через `status`/`isActive`-булев и никогда через физический DELETE.**
Смотри как эталон `server/src/modules/nomenclature/nomenclature.routes.js`
(`DELETE /:id` — просто `update({ archivedAt: new Date() })`, без
проверки на существующие ссылки). Читающие запросы фильтруют
`archivedAt: null` только там, где идёт **выбор для нового** объекта
(создание заказа, комбобоксы); в `include` для уже существующих
заказов/перемещений фильтра нет — значит архивная запись продолжает
корректно отображаться в истории. Это уже проверено на примере
номенклатуры в `orders.routes.js` (создание заказа фильтрует
`archivedAt: null` на `NomenclatureItem.findOne`, а `include` в GET
заказа — без фильтра). **Обязательно перепроверь тот же факт для
`Location`**: найди все места, где `Location` подключается через
`include` в исторических выборках заказов/перемещений (`orders.routes.js`,
`transfers.routes.js`, отчёты в `server/src/modules/reports/`), и
убедись, что там нет `where: { archivedAt: null }` на самой `Location`.
Если есть — это баг, из-за которого архивная точка приёма исчезнет из
уже закрытых заказов в отчётах; убери фильтр именно в исторических
`include`, оставь только в местах выбора для новых объектов.

### Backend

Сейчас для `locations`/`branches` вообще нет CRUD-роутов — только
чтение через `GET /api/v1/auth/context`
(`server/src/modules/auth/auth.routes.js`, ~строки 101-138), которое
уже фильтрует `archivedAt: null` на `Branch` и вложенных `Location`.
`locations` сейчас только сидируются (`server/src/database/seed.js`,
~строки 100-142).

Создать новый модуль `server/src/modules/locations/locations.routes.js`
по образцу `nomenclature.routes.js` (структура: zod-схемы
`createInput`/`updateInput`, `success()`-обёртка, роуты через
`requirePermission`):

- `GET /locations` — список, `where: { archivedAt: null }` по
  умолчанию, `?includeArchived=true` — без фильтра (для admin-вида с
  переключателем «Показать архивные», см. паттерн `showAllStatuses` в
  `client/src/pages/PriceListsPage.jsx`).
- `POST /locations` — создание (`branchId`, `code`, `name`, `type`).
  Уникальный индекс `(branchId, code)` уже есть на уровне БД — на
  конфликте вернуть внятную `ApiError` (посмотри, как обрабатывается
  `SequelizeUniqueConstraintError` в `catalog.routes.js` или
  `price-lists.routes.js`, если там уже есть паттерн, и повтори его).
- `PATCH /locations/:id` — редактирование `name`/`code`/`type`. Не
  давай менять `branchId` при редактировании (репривязка к другому
  филиалу — это по сути другая точка; если понадобится, пусть создают
  новую и архивируют старую).
- `DELETE /locations/:id` — тот же паттерн, что у номенклатуры:
  `update({ archivedAt: new Date() }, { where: { id, organizationId, archivedAt: null } })`,
  без проверки на ссылки. Перед этим шагом на клиенте (см. ниже)
  сделать **некритичное предупреждение**, если у точки есть открытые
  заказы/активные перемещения — но не блокировать архивирование.
- `PATCH /locations/:id/restore` (или флаг в `PATCH /:id`) — снять
  `archivedAt`, чтобы архивирование было обратимым прямо из UI.

Права — через `requirePermission('settings.manage')`. Этот код уже
заведён в `server/src/database/seed.js` (~строка 65), но нигде не
используется — это первый модуль, который его задействует. Проверь,
что роль `owner`/`admin` в сиде реально имеет этот permission
привязанным (посмотри `RolePermission`/аналог в `seed.js`), иначе
демо-пользователь `owner@example.invalid` не сможет пройти
`requirePermission`.

Зарегистрировать роутер в `server/src/app.js` (по образцу строки 54:
`app.use('/api/v1/nomenclature', createNomenclatureRouter(...))`) —
`app.use('/api/v1/locations', createLocationsRouter({ sequelize, env }))`.

Backend-тест: добавить интеграционный тест по образцу существующих в
`server/src/tests/business-workflow.integration.test.js` — создание,
редактирование, архивирование, восстановление, плюс проверка что
архивная locations всё ещё видна в GET уже созданного заказа
(регрессионный тест именно на "не задевает отчётность" — это ядро
задачи, тест обязателен, не пропускай).

### Порядок работы

1. Backend: модуль, роуты, регистрация в `app.js`, интеграционный тест
   (включая регрессионный тест на видимость архивной локации в истории
   заказа).
2. `pnpm --recursive test` — зелёный, включая новый тест.
3. Frontend: services/queries/mutations/schema, страница, пункт
   навигации, инвалидация `auth-context`.
4. `pnpm lint` + `pnpm --recursive test`.
5. Визуальная проверка вживую (temp Playwright `.mjs` из корня репо,
   логин `owner@example.invalid` / `DevPass123!`, клики по сайдбару —
   не `page.goto()` на внутренний роут, токен только в памяти):
   создать точку, отредактировать, архивировать, убедиться что она
   пропала из селектов в «Создать заказ», убедиться что уже созданный
   заказ с этой точкой приёма/выдачи всё ещё открывается и показывает
   её название. Восстановить точку, убедиться что она вернулась в
   селекты. Удалить скрипт и скриншоты после проверки.
6. Коммит после каждого законченного логического куска (backend
   отдельно, frontend отдельно) — не копить в один гигантский коммит.

### Открытый вопрос, который не блокирует работу

Управление самими `branches` (филиалами) сознательно оставлено вне
скоупа — они как были, так и остаются только сидируемыми. Если по ходу
станет ясно, что Павлу нужно ещё и создавать филиалы (а не только
точки внутри существующего) — это отдельная, отдельно согласуемая
задача, не блокирует и не входит в эту.
