# HANDOFF: улучшения CleanFlow ERP после REST-миграции

> Этот файл — для новой рабочей сессии/другой модели. Открой его первым
> делом и следуй ему. Роль и архитектурные принципы уже описаны в
> `PROJECT_CONSTITUTION.md` и подгружаются автоматически через
> `CLAUDE.md` — они обязательны и здесь не дублируются.

## Контекст: что уже сделано

Предыдущая сессия завершила перевод фронтенда на REST-ориентированную
архитектуру: все ~70 вызовов `apiClient`, которые раньше были раскиданы
по страницам, теперь лежат в `client/src/services|queries|mutations/*.js`
по одному модулю на ресурс (catalog, services, defect-groups,
nomenclature, price-lists, clients, production, transfers, reports,
payments, files, measurements, orders, auth-context). `auth` (login/
refreshSession/logout/getCurrentUser) осознанно оставлен в
`client/src/api/client.js` — единственный потребитель (`App.jsx`), не
пересекается ни с чем, переносить незачем.

Этот файл описывает **следующий этап** — не архитектуру данных, а
качество кода, UX и надёжность поверх неё. Ниже — результат анализа
всего приложения (клиент + сервер), с конкретными находками и
приоритетами. Не переизобретай анализ заново — де-факто он уже
проведён, здесь нужно действовать.

## Стек и как поднять проект

- pnpm-монорепо: `server/` (Express 5 + Sequelize + Postgres), `client/`
  (React 19 + Vite + React Query + Zustand — Zustand заявлен, но не
  используется, см. ниже).
- Локальный Postgres — служба Windows `postgresql-x64-18`, не Docker.
- Поднять: `node server/src/server.js` (порт 3000) и
  `pnpm --filter @cleanflow/client dev` (порт 5173, если занят — Vite
  сам поднимется на 5174).
- Логин: `owner@example.invalid` / `DevPass123!`
- Перед стартом прогони `pnpm lint` и `pnpm --recursive test` — всё
  должно быть зелёным, прежде чем добавлять свои изменения.

## Находки

### Сильные стороны (не трогать, не переделывать "чтобы было красивее")
- Слой данных после миграции единообразен, ключи кэша React Query не
  дублируются между файлами.
- `useOrderHotkeys` и вообще внимание к скорости работы приёмщика.
- OpenAPI-контракт (`docs/api-contract.md`, `openapi.json`) реально
  соответствует бэкенду.
- Разумные дефолты React Query в `client/src/main.jsx`
  (`staleTime: 30_000`, `retry: 1`, `refetchOnWindowFocus: false`).
- Есть настоящий интеграционный тест на реальной БД
  (`server/src/tests/auth.integration.test.js`), не только моки.

### Слабые места
- **`client/src/pages/OrdersPage.jsx` — 1051 строка**, в одном файле
  четыре компонента (`OrdersPage`, `OrderEditor`, `RemoveServiceButton`,
  `OrderMetaValue`). Прямое нарушение собственного правила проекта
  ("Pages orchestrate only... Never place large business logic inside
  pages"). Данные вынесли, JSX/раскладку — нет.
- **Zustand, React Hook Form, Zod — в `client/package.json`, но нигде
  не используются** (проверено grep'ом по всему `client/src`). Все
  формы — это `useState` + вручную написанные `onChange`-хендлеры,
  валидация — только нативные HTML-атрибуты (`required`, `minLength`).
  Конституция требует эти библиотеки как предпочтительные — по факту
  этого нет, паттерн формы дублируется вручную в 15+ файлах
  (`ClientEditModal.jsx`, `OrderMetaEditor.jsx`, `NomenclaturePage.jsx`,
  `CatalogPage.jsx` и т.д.).
- **`client/src/styles/global.css` — 2331 строка**, единственное
  исключение с CSS Modules — `InfrastructurePage.module.css`. Риск
  конфликтов имён классов, сложно понять, что ещё используется.
- **Тесты бэкенда не покрывают бизнес-логику.** Есть тесты на auth,
  authorization, схему БД, генерацию номера заказа, расчёт даты,
  печать, openapi-контракт (`server/src/tests/*.test.js`) — но ни
  одного прямого теста на сами модули `orders`, `production`,
  `transfers`, `payments`, `price-lists` (`server/src/modules/*`).
- **Нет `ErrorBoundary`** нигде в дереве React-компонентов — любое
  необработанное исключение в рендере валит всё приложение в белый
  экран.

### UX
- **Нет real-time синхронизации между рабочими местами.** ERP
  рассчитан на одновременную работу приёмщика/кассира/производства
  (см. PROJECT_CONSTITUTION.md → PROJECT). При `staleTime: 30s` и без
  polling/websocket кассир может 30+ секунд не видеть, что заказ уже
  отменён приёмщиком (или наоборот) — конкретный источник ошибок в
  реальной работе, не абстрактный.
- `ClientPickerModal`/`OrderItemPickerModal` требуют минимум 2 символа
  для поиска и не показывают недавних/частых клиентов.
- Нет глобального уведомления о недоступности сети/сервера — только
  точечные `form-error` внутри конкретных форм.
- Много `window.confirm()` (отмена заказа, выдача заказа) — нативный
  диалог не стилизуется и не вписывается в UI на кассовом терминале.

### Производительность
- Нет `React.lazy`/code-splitting по роутам — весь клиент в одном
  бандле.
- В `WorkspacePage.jsx` запросы `operational`/`financial` отчётов
  включены и на `overview`, и на `reports` — рефетч обоих отчётов при
  заходе в любой из двух разделов.
- Почти нет `useMemo`/`React.memo` в тяжёлых списках (`OrderListPanel`,
  список позиций заказа) — пока незаметно на демо-данных (20 заказов),
  но не масштабируется.

## Приоритеты

### Critical
1. Добавить `ErrorBoundary` на уровень `App.jsx`/`WorkspacePage.jsx`.
2. Решить вопрос синхронизации данных между рабочими местами хотя бы
   для заказов/оплат — не обязательно websocket, можно короткий
   polling для активных заказов или `staleTime: 0` + рефетч по
   релевантным событиям.

### Important
3. Разбить `OrdersPage.jsx`: вынести `OrderEditor` в
   `features/orders/OrderEditor.jsx`, `RemoveServiceButton` и
   `OrderMetaValue` — в `OrderItemControls.jsx` или отдельные файлы.
   Страница должна остаться тонким контейнером.
4. Определиться с Zustand/React Hook Form/Zod: либо реально внедрить
   (RHF + Zod особенно оправданы для форм вроде `ClientEditModal`,
   `OrderMetaEditor`, `NomenclaturePage` — сильно сократят
   дублирование), либо убрать из зависимостей и из
   `PROJECT_CONSTITUTION.md`, раз фактически не используются.
   Расхождение декларируемого стека и реального кода — само по себе
   риск для будущих сессий.
5. Покрыть тестами бэкенд-модули `orders`/`payments`/`production` —
   сейчас самое дорогое место для необнаруженной регрессии.

### Later
6. Перевести страницы на CSS Modules вместо роста `global.css`.
7. Code splitting по роутам (`React.lazy`).
8. Заменить `window.confirm()` на стилизованные модалки подтверждения.

## Как проверять изменения

Тот же процесс, что и в прошлой сессии, он себя оправдал — держись его:

1. `pnpm lint` и `pnpm --recursive test` до и после каждой завершённой
   задачи.
2. Временный `.mjs`-скрипт на Playwright из **корня репозитория** (не
   из scratch-директории — иначе не найдёт `node_modules`), чтобы
   реально пройти сценарий в браузере (`chromium.launch()`, логин,
   клики по реальным элементам UI, скриншот, прочитать скриншот
   инструментом чтения) — не полагайся только на прохождение тестов.
   Удаляй скрипт после проверки.
3. При навигации по приложению в Playwright — кликай по реальным
   элементам UI (сайдбар, кнопки), а не `page.goto()` на внутренний
   роут: токен доступа хранится только в памяти (`apiClient`), полная
   перезагрузка страницы его сбрасывает.
4. `getByRole`/`getByText` без `exact: true`, если в тексте кнопки
   сайдбара смешаны иконка и подпись — точное совпадение часто не
   срабатывает.
5. Коммить и пушить после каждой завершённой задачи отдельным
   коммитом — не копить всё в один гигантский коммит.
